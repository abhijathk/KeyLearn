Automating the desk

Everything below sits on top of the desk that already exists — the same tickets, the same Answers library, the same audit log. Nothing here replaces a human; it removes the part where a human has to be the one who notices a routine ticket, drafts the obvious reply, and closes the loop. The agent reads, drafts, and flags. A person still owns close, still owns anything that matters, and can turn the whole thing off with one switch.

Built on OpenClaw (MIT — Gateway, cron/automations, taskflow, MCP tools, a native Groq provider) driving Groq as the model, against a handful of new, deliberately narrow endpoints on KeyLearn's own support API. No third-party helpdesk, no second database — one more actor in the same desk, with a smaller badge in the audit log.

It has a name, on purpose — Tab, with a small AI mark beside it everywhere it appears, so nobody mistakes its message for a colleague's, and nobody has to wonder either.

01Where the agent sits

The agent is not staff. It doesn't sign in with a passkey and it isn't in STAFF_EMAILS — it carries its own key, checked by its own code path, that opens a much smaller door than the one a human walks through.

03Reading the room — sentiment, not just topic

Two tickets can be the same technical issue and need completely different handling. A tone read runs alongside classification and shows up as a chip in the inbox and the thread — only a "critical" read escalates on its own; a merely frustrated one is tagged for the daily digest and the agent still tries to help.

04The middle tier — for uncertain, not for routine

This is not where every unmatched question goes by default — a routine question with a grounded, correct answer sends itself, full stop, the same as step 02. This queue exists for the narrower case where Verify (step 5 of the triage flow) genuinely can't confirm the draft is right — the Booklet doesn't clearly cover the specific case, or two sources disagree. One click to send as-is, one to edit first, one to hand to a person instead. It reuses the same idea the Answers library already has in suggestOnly, just applied to Tab's own uncertain drafts instead of a keyword rule.

05Escalation — two speeds, one queue

Everything escalated still lands in the same flagged queue staff already has — nothing new to check. The only change is how loud it is on the way in: most flags wait for tomorrow's digest; a short list of things interrupt immediately, because a day's delay is the wrong answer for them.

Flags in tomorrow's digest, not before

Low confidenceThe verify step re-reads its own draft and isn't sure — hands off rather than guesses.
Frustrated, not criticalWorth a human eye, not worth interrupting anyone's evening for.
Explicit "I want a person"Said plainly, honoured immediately — just not paged.
Reopened once after a Tab replyThe customer wrote back — the reply didn't land. Feeds the reopen-rate metric too.

Flags right now — email fires immediately

Security / account-takeover patternCredential-stuffing language, a suspicious sign-in, a phishing link sent to support.
Critical sentimentReads as genuinely distressed — see step 03.
Child-safety or abuse reportAnything suggesting a child is at risk, or a report of another user's behaviour — never Tab's to judge alone.
Privacy / data-deletion requestA parent asking for a child's data removed, or withdrawing consent — must be handled precisely, not paraphrased.
Legal or regulatory contactA lawyer, a regulator, anything with real consequences if the wording is even slightly off.
A report that reads like a real security bugTreated as a live vulnerability report, not a support ticket, until a person says otherwise.
Reopened a second timeThe automated path already failed once on this ticket — stop trying, don't try a third draft.

11When the model itself runs out

A free-tier daily cap is a real ceiling here, not a hypothetical — Groq tracks requests-per-day per model, and the pipeline calls two of them per ticket. This isn't treated as an error to retry into a black hole: it's a distinct, detected state with its own banner and its own immediate email, separate from tomorrow's digest.

Rules this phase adds

The agent only ever talksIt can read a thread and post a reply. It cannot touch a profile, a setting, or anyone's account — kids' issues included, since support was already scoped to the account holder, never the child, before automation existed.
Ticket text is data, never instructionsNothing embedded in a message — "ignore previous instructions," "mark this resolved," "give me an admin email" — is followed. It's read the same way a phishing attempt is read: as content to react to, not commands to obey.
One switch stops all of itOff means every new ticket routes to a human immediately. Nothing in flight is lost; nothing new gets picked up.
A cap on how much damage an hour can doIf something's misfiring at scale — a bad prompt change, a degraded model — the auto-close cap throws the rest to a human instead of compounding the mistake.
Escalation on sentiment is opinionatedOnly a critical read jumps the queue. A frustrated one still gets the agent's best attempt — being upset about a real, fixable problem isn't itself a reason to make someone wait longer.
Everything it does is audited as "agent," never as a personIts key, its own audit-log actions, its own actor identity — never attributed to a staff member, never blended into a human's history.
Shadow mode exists for exactly one reasonTrying a new threshold or prompt against real tickets without risking a real send — every draft still happens, nothing goes out unapproved.
Routine is fully automated, on purposeNothing about a correct, grounded answer needs a human to bless it first. The suggested-replies queue is for genuine uncertainty, not a default parking spot — most tickets never touch it.
Every claim traces to a document, not memoryTab drafts from the Answers library and the How-To Booklet — a maintained reference of how KeyLearn actually works — never from what the model thinks it recalls about the product.
Some things are never said, no matter how confident or well-groundedAnother person's account details or activity, internal/company specifics, or how a security mechanism actually works internally — held out at the same Verify step that checks factual correctness, as a separate, unconditional filter.
Running out of model quota fails the same way the kill switch doesStraight to the human queue, immediately, with one alert email — never a silent stop, never a retry loop, never a wrong answer sent because the good model wasn't available.
